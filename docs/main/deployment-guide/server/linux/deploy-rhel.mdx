Install Mattermost Server on Red Hat Enterprise Linux (RHEL), Rocky Linux, AlmaLinux, Oracle Linux 7+, or CentOS Stream. RHEL doesn't have a signed APT-style repository, so this guide installs from the release tarball with manual systemd setup, then walks through the security configuration RHEL deployments typically need (SELinux contexts, firewalld rules, fapolicyd allow rules).

<Note title="Minimum requirements">

- **Operating system**: RHEL 7+, Rocky / Alma 8+, Oracle Linux 7+, CentOS Stream 8+.
- **Hardware**: 1 vCPU and 2 GB RAM (supports up to ~1,000 users).
- **Database**: [PostgreSQL 14+](/administration-guide/manage/admin/postgres-migration).
- **Network**: TCP 80/443 inbound (TLS), 8065 inbound (System Console), 10025 outbound (SMTP relay if used).

</Note>

## Step 1: Get a PostgreSQL database

Choose one of:

- **Install PostgreSQL locally** on the same host. See the [PostgreSQL installation documentation](https://www.postgresql.org/download/).
- **Use an external PostgreSQL server** and collect connection credentials before Step 2.
- **Use a managed database service** (AWS RDS, Azure Database for PostgreSQL, etc.).

## Step 2: Prepare the database

Follow the [database preparation](/deployment-guide/server/prepare-database) instructions to create the Mattermost database, user, and grants.

## Step 3: Download the Mattermost Server tarball

SSH onto the target host and download the release. Replace `amd64` with `arm64` for ARM-based hardware.

## Step 4: Install Mattermost Server

Update existing system packages first:

```sh
sudo dnf update
sudo dnf upgrade
```

Extract the tarball and move it into place:

```sh
tar -xvzf mattermost*.gz
sudo mv mattermost /opt
```

<Note title="Files, plugins, and the service user">

On a new installation, `mattermost setup` creates the `mattermost` system user when it is missing. It stores files in `/var/lib/mattermost/data`, plugins in `/var/lib/mattermost/plugins` and `/var/lib/mattermost/client/plugins`, and logs in `/var/log/mattermost`. An existing installation keeps the paths it already uses. Pass `--uid` when this host must match a shared-storage uid. Setup does not change an existing user.

</Note>

Copy the unit shipped with the tarball:

```sh
sudo cp /opt/mattermost/config/mattermost.service /etc/systemd/system/mattermost.service
sudo systemctl daemon-reload
```

<Note>

Earlier versions of this guide had you write the unit file by hand, or place it under `/lib/systemd/system/`. `/lib/systemd/system/` is reserved for unit files installed by a package manager. The shipped unit loads `/etc/mattermost/mattermost.env`.

</Note>

## Step 5: Configure and start the server

Run setup as root. It writes `/etc/mattermost/mattermost.env` (mode `0600`) and points the unit at that file. By default the active configuration is stored in PostgreSQL. Setup does not enable or start the service.

```sh
sudo /opt/mattermost/bin/mattermost setup
sudo systemctl enable --now mattermost
curl http://localhost:8065
```

You should see the Mattermost HTML response.

On a new installation, setup asks for the PostgreSQL URL and the Site URL. A non-interactive install:

```sh
printf '%s\n' 'postgres://mmuser:<mmuser-password>@<host>:5432/mattermost?sslmode=disable' | sudo tee /root/mattermost-database.url >/dev/null
sudo chmod 600 /root/mattermost-database.url
sudo /opt/mattermost/bin/mattermost setup \
  --database-url-file /root/mattermost-database.url \
  --site-url 'https://mattermost.example.com' \
  --non-interactive
```

The URL file keeps the password out of the shell history and the process list. Remove it after setup. `--database-url -` reads one line from stdin instead.

Pass `--config-store file` to keep configuration in a file. Setup then writes `/etc/mattermost/config.json` and sets `MM_CONFIG` to that path.

Once the environment file is in place, Mattermost does not read `/opt/mattermost/config/config.json`. Change settings afterward in the System Console, with `mmctl`, or by editing `/etc/mattermost/config.json` when you chose file storage. Set [`SupportSettings.SupportEmail`](/administration-guide/configure/site-configuration-settings#support-email-address) to the address users contact for help.

An existing server that already has configuration in PostgreSQL can be joined with the same command. Setup reports that this is an existing installation, checks connectivity, and writes this host's environment file. It adds a systemd drop-in only when the unit does not already load that file. It does not change the stored configuration or the Site URL. Do not run setup as part of a version upgrade.

If start fails on a hardened RHEL system, continue to the [Hardened RHEL configuration](#hardened-rhel-configuration) section below before troubleshooting elsewhere — it's almost always SELinux, firewalld, or fapolicyd.

Tarball-based installs are upgraded manually. See [Upgrading Mattermost Server](/administration-guide/upgrade/upgrading-mattermost-server).

## Hardened RHEL configuration

Hardened RHEL installs typically require additional configuration for SELinux, firewalld, and fapolicyd. Each is covered below.

<Tabs>
<TabItem value="selinux" label="SELinux" default>

RHEL 9 ships with SELinux in enforcing mode. Verify with `sestatus`. If it's enforcing, set the appropriate contexts before starting Mattermost.

**Set the binary context** for `/opt/mattermost/bin`:

```sh
sudo semanage fcontext -a -t bin_t "/opt/mattermost/bin(/.*)?"
sudo restorecon -RF /opt/mattermost/bin
```

**Set the directory context** for `/opt/mattermost`. Check current context:

```sh
ls -Z /opt/mattermost
```

If the type is `default_t`, set a web-application context:

```sh
sudo semanage fcontext -a -t httpd_sys_content_t "/opt/mattermost(/.*)?"
sudo restorecon -R /opt/mattermost
```

A stock enforcing system does not ship a Mattermost policy. With `/opt/mattermost/bin` labeled `bin_t`, systemd starts the service unconfined, and that domain can write the default types on `/var/lib` (`var_lib_t`) and `/var/log` (`var_log_t`). `/etc/mattermost/mattermost.env` is mode `0600` and is read by systemd as root, so it needs no extra label.

If a local policy confines Mattermost and the audit log shows denials for the new directories, label them writable:

```sh
sudo semanage fcontext -a -t httpd_sys_rw_content_t "/var/lib/mattermost(/.*)?"
sudo semanage fcontext -a -t httpd_sys_rw_content_t "/var/log/mattermost(/.*)?"
sudo restorecon -R /var/lib/mattermost /var/log/mattermost
```

**Allow Mattermost to bind to port 8065** (or your configured port):

```sh
sudo semanage port -l | grep 8065
sudo semanage port -a -t http_port_t -p tcp 8065
```

**Generate a custom policy** if SELinux blocks something specific. Check denials:

```sh
sudo ausearch -m avc -ts recent
sudo cat /var/log/audit/audit.log | grep denied
```

Generate a policy module from those denials:

```sh
sudo yum install -y policycoreutils-python-utils
sudo grep mattermost /var/log/audit/audit.log | audit2allow -M mattermost_policy
sudo semodule -i mattermost_policy.pp
```

**Restart and verify**:

```sh
sudo systemctl restart mattermost
```

<Tip title="Testing-only fallback">

For debugging, you can temporarily switch SELinux to permissive mode with `sudo setenforce 0`. Re-enable enforcement with `sudo setenforce 1` once contexts are correct. Don't ship a production deployment in permissive mode.

</Tip>

**References**

- [SELinux User's and Administrator's Guide](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/7/html/selinux_users_and_administrators_guide/index)
- [SELinux Project Wiki](https://github.com/SELinuxProject/selinux)

</TabItem>
<TabItem value="firewalld" label="firewalld">

firewalld is the default firewall on RHEL. Check status:

```sh
sudo systemctl status firewalld
```

**Open the Mattermost ports**:

```sh
sudo firewall-cmd --permanent --add-port=8065/tcp
sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --reload
sudo firewall-cmd --list-all
```

The output should show `8065/tcp` and the `http` / `https` services.

**Mattermost Calls ports** (if you're running the Calls plugin or the standalone rtcd service):

```sh
# Integrated Calls plugin
sudo firewall-cmd --permanent --add-port=8443/udp
sudo firewall-cmd --permanent --add-port=8443/tcp
sudo firewall-cmd --reload

# Standalone rtcd (adds API port)
sudo firewall-cmd --permanent --add-port=8045/tcp
sudo firewall-cmd --reload
```

- Port 8443 (UDP/TCP) carries RTC media (audio, video, screen share).
- Port 8045 (TCP) is the rtcd API.
- TCP support for RTC requires Calls v0.17+ and rtcd v0.11+.

See the [Calls deployment guide](/deployment-guide/calls/calls-deployment-guide) for the full topology.

</TabItem>
<TabItem value="fapolicyd" label="fapolicyd">

fapolicyd (File Access Policy Daemon) blocks execution of untrusted binaries. In secure RHEL environments it commonly blocks Mattermost binaries and plugins — the symptom is "operation not permitted" errors in `mattermost.log`.

**Confirm fapolicyd is the cause** by temporarily stopping it:

```sh
sudo systemctl stop fapolicyd
sudo systemctl start mattermost
```

If Mattermost now works, restart fapolicyd and configure an allow rule.

**Identify the denial**:

```sh
sudo fapolicyd --debug
```

Look for a line like:

```text
rule=15 dec=deny_audit perm=execute auid=-1 pid=19735
  exe=/opt/mattermost/bin/mattermost : path=/opt/mattermost/plugins/focalboard/server/dist/plugin-linux-amd64
  ftype=application/x-executable trust=0
```

Note the rule number — your allow rule must be numbered lower so it's evaluated first.

**Create an allow rule** at `/etc/fapolicyd/rules.d/80-mattermost.rules`:

```text
allow perm=execute exe=/usr/bin/sudo trust=1 : dir=/opt/mattermost/ all trust=0
allow perm=execute exe=/opt/mattermost/bin/mattermost : dir=/opt/mattermost all trust=0
allow perm=execute exe=/opt/mattermost/bin/mattermost : dir=/var/lib/mattermost all trust=0
allow perm=execute exe=/usr/lib/systemd/systemd trust=1 : dir=/opt/mattermost/ all trust=0
allow perm=execute exe=/usr/lib/systemd/systemd trust=1 : dir=/var/lib/mattermost/ all trust=0
```

A new installation runs server plugins from `/var/lib/mattermost/plugins`. The `/opt/mattermost` rules do not cover that directory.

**Validate and load**:

```sh
sudo fagenrules --check
sudo fagenrules --load
sudo systemctl restart fapolicyd
sudo systemctl restart mattermost
```

Verify:

```sh
curl http://localhost:8065
sudo systemctl status mattermost
```

**Rules for the standalone rtcd service** (if deployed): create `/etc/fapolicyd/rules.d/80-rtcd.rules`:

```text
allow perm=execute exe=/usr/bin/sudo trust=1 : dir=/opt/rtcd/ all trust=0
allow perm=execute exe=/opt/rtcd/bin/rtcd : dir=/opt/rtcd all trust=0
allow perm=execute exe=/usr/lib/systemd/systemd trust=1 : dir=/opt/rtcd/ all trust=0
```

Then reload fapolicyd as above. See [RTCD Setup and Configuration](/deployment-guide/calls/calls-rtcd-setup) for the full rtcd install path.

<Note title="Rule numbering">

fapolicyd rules are evaluated in order. Your allow rules must be numbered lower than the deny rule that's blocking Mattermost — `80-` is usually safe with a stock configuration. If denials persist, re-check the rule number from `fapolicyd --debug` and renumber accordingly.

</Note>

**Reference**: [Mattermost and fapolicyd](https://support.mattermost.com/hc/en-us/articles/12167526545172-Mattermost-and-fapolicyd) support article.

</TabItem>
</Tabs>

## Remove Mattermost

Stop the server, back up any data you need, then remove the install directory:

```sh
sudo systemctl stop mattermost
sudo rm -rf /opt/mattermost
sudo rm -f /etc/systemd/system/mattermost.service
sudo rm -rf /etc/systemd/system/mattermost.service.d
sudo userdel mattermost
```

<Important title="Back up before removing">

An install that used `mattermost setup` keeps files in `/var/lib/mattermost`, logs in `/var/log/mattermost`, and configuration in `/etc/mattermost`. Back those up before deleting them. Older installs may still keep `config/`, `logs/`, `plugins/`, `client/plugins/`, and `data/` under `/opt/mattermost`.

</Important>
